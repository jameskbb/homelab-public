# What I learned building a homelab

## Start with a job, not a shopping list

The project became useful when every addition answered a simple question: what
problem does this solve at home? A start page reduces friction. Monitoring tells
me when something is unavailable. Game servers create a shared place for
friends. Those jobs made the project easier to prioritize than a list of
hardware upgrades.

## Ordinary hardware is enough to begin

An office desktop with a capable processor, enough memory, and two drives has
been a great starting point. It is quiet, compact, inexpensive compared with
server hardware, and powerful enough for several small workloads. I can learn
the habits before spending money on bigger equipment.

## Separation reduces stress

Keeping applications, games, and experiments in different virtual computers
makes a practical difference. When a game update goes sideways, it does not
need to affect the home dashboard. When I try an experimental tool, it is not
sharing its operating system with everything else.

## Monitoring changes the feeling of running things

A simple health dashboard turns "I hope it still works" into a quick answer.
It is especially useful after an update, power event, or maintenance window.
Monitoring does not fix a problem, but it tells me where to look first.

## Backups become real at restore time

Making a backup is easy to check off. Recovering from one is the useful test.
I now treat a successful restore as part of the project, not an emergency-only
task. That practice uncovered assumptions about data, permissions, and startup
order that a backup log would never reveal.

## Public sharing needs a different kind of documentation

The private build notes are detailed because they must support operation and
recovery. Public notes have a different job: explain the decisions, the
learning, and the outcomes without sharing internal routes, service links,
account details, or secrets. Both documents can be honest, but they should not
be the same document.
